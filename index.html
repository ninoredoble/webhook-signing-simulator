Sign a webhook.
Watch it retry.

Two things every webhook sender has to get right: sign each request so the receiver can trust it, and retry failures without flattening the receiver when it comes back. This page lets you do both with your own hands, using the browser's built-in HMAC-SHA256.

Sign a payload Compare retry strategies

This is a simulator. It is a static page, a study in how these two mechanisms behave. Nothing is sent over the network, there is no server or queue behind it, and the sample events, amounts and secret are made up. Do not paste a real secret into it.

Sign a payload

        

          The sender joins the timestamp and the exact request body with a dot, then computes an HMAC-SHA256 of
          that string using a secret shared with the receiver. The result goes in a header. The header name
          and format here follow common webhook conventions, but Relay-Signature is a name made up for this study.

Verify as the receiver

        

          The receiver never trusts the header on its own. It checks the timestamp is recent, so an old capture can't be replayed,
          recomputes the signature from the body it actually received, and compares in constant time.
          Break something in transit and see which check catches it.

    Retry with backoff
    
        
    
          The subscriber's endpoint fails the first few attempts, then recovers. Four ways of choosing the wait before the next try,
          run on the same settings and the same random seed. The pale bar behind each wait is the longest it could have been;
          the solid bar is what it was.
        
    

        
    
          
    
            
    
              
    
                
                
              
    
              
    
                
                
              
    
              
    
                
                
              
    
              
    
                
                
              
    
              
    
                
                
              
    
              
    
                
                
              
    
            
    
            
    
              
              
            
    
          
    

          
    
            
    
            
    
            
    
            
    
              
    
                When each strategy sends attempt n, in seconds after the first try. Decorr. is decorrelated jitter.
                
                
              
    
            
    
          
    
        
    

        
    
          
    The four waits
    
          
    
            After the kth failure, let d = min(cap, base × multiplier^(k−1)).
          
    
          
      
            
    • No jitter: wait d.
      • 
            
    • Full jitter: wait a random time between 0 and d.
      • 
            
    • Equal jitter: wait d/2 plus a random time between 0 and d/2.
      • 
            
    • Decorrelated jitter: wait a random time between base and three times the previous wait, never above cap.
      • 
          
    
          
    These are the strategies compared in the AWS Architecture Blog post “Exponential Backoff and Jitter”. The code here is written from that description for this study.
    
        
    
      
    

      
    
        
    Why the jitter
    
        
    
          One client retrying alone looks fine either way. The trouble is many clients that failed at the same instant.
          Here, 200 subscribers all fail every attempt. Each chart counts how many of their first four retries land in each slice of time,
          using the settings above. Same clients, same scale on every chart.
        
    
        
    
        
    
          Spreading retries out is not the same as thinning them early. Full jitter can pick a very short wait, so it still bunches up
          near the start; equal and decorrelated jitter keep a floor under the wait. Change the settings above and compare the numbers,
          not just the shapes.
        
    
      
    

      
    
        
    What this is, and is not
    
        
    
          
    
            
    It is
    
            
      
              
    • A static HTML, CSS and JavaScript page with no dependencies and no build step.
      • 
              
    • Real HMAC-SHA256 through the browser's Web Crypto API. You can check it against a published test vector above.
      • 
              
    • A seeded simulation of four retry strategies. Same seed, same result, so you can compare changes.
      • 
              
    • A study I built to understand these mechanisms, and to explain them.
      • 
            
    
          
    
          
    
            
    It is not
    
            
      
              
    • A webhook delivery service, an API, or something running in production. There is no backend, queue, database or cache.
      • 
              
    • Connected to anything. It makes no requests of its own and sends no data anywhere.
      • 
              
    • Code to copy into a real receiver. The signature comparison is written to be constant-time, but JavaScript makes no such guarantee. Use your platform's own helper for real work.
      • 
              
    • Using real data. Events, amounts and the secret are illustrative.
      •

cd webhook-signing-simulator
python3 -m http.server 8000   # then open http://localhost:8000
    
        
    
        
    Web Crypto needs a secure context, which both localhost and the hosted page provide.
